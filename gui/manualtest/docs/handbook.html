gui-test

gui-test Handbook

gui-test turns the manual test descriptions for cppcheck-gui into automated tests: Claude explores the GUI once and writes a script, and from then on the script is replayed without any AI.

Updated 2026-10-22

Overview

A test is written in plain words: steps and an expected result. gen.py starts the application, lets Claude do the test by hand through guitest.py, and saves what it did as a script of do and expect steps. run.py replays the scripts, one fresh application per test, and writes an HTML report. web.py is the web interface around all of it.

The application runs in its own Xvfb display with its own D-Bus and accessibility bus, so your desktop is never touched. Elements are found through AT-SPI by their accessible name and role, not by screen positions.

PartWhat it does
web.pyWeb interface: edit test files and test projects, generate scripts, run tests, open reports
gen.pyClaude drives the GUI once per test and writes its script; the script is saved only if a replay passes

results/One directory per run with the report, logs and screenshots

Getting started

Start web.py with the cppcheck-gui binaries you want to test, then open http://127.0.0.1:8080/ in a browser.

./web.py --opensource ~/cppcheck/build/bin/cppcheck-gui \
         --premium ~/premium/build/bin/cppcheck-gui --src ~/cppcheck
  • --opensource and --premium each take the binary of that edition. Give one, both or none; without a binary you can edit tests but not generate or run them.
  • --src is the git checkout the binaries are built from. It is only used for the git SHA, branch and commit in the report; the default is the directory of the binary.
  • --dir (default tests), --out (default results) and --port (default 8080) change where test files and results live and which port is used. The server only listens on 127.0.0.1.

The tools the session needs must be installed: Xvfb, xdotool, dbus-daemon, the AT-SPI bus launcher and Python with the GObject bindings and Pillow. tesseract is only needed for ocr checks, and the claude command line tool only for generating scripts. On Ubuntu (checked on 26.04) they come from these packages:

sudo apt install xvfb xdotool dbus at-spi2-core python3-gi gir1.2-atspi-2.0 python3-pil tesseract-ocr tesseract-ocr-eng

The web interface

  • Left column: the test files and the test projects. The ▶ button next to a file runs all tests in it.
  • Header: Save, Run all (every test in every file), the edition picker (opensource, premium or both) and a status message.
  • Main area: the open test file, the open test or test project. Each has an ✕ in the top right corner to close it.
  • Job box: while a script is generated or tests run, it shows the progress, the results as they come and a link to the report. Its ✕ hides it until the next job.

Writing tests

A test is written as if for a person: steps in plain words and the result to expect. Claude reads exactly these words when it makes the script, so be concrete.

Tests live in test files (tests/*.json), one file per area of the GUI. Click a file in the left column to see its title and its tests, New file to create one, or Import .md to convert an older markdown test file (sections ## Test: NAME). Click a test in the list to edit it, + New test to add one. Nothing is written to disk until you press Save; a dot after the file name means there are unsaved changes.

FieldWhat to write
NameUnique within the file. Shown in reports and the history, so a rename starts a new history line
TicketOptional, e.g. a Trac ticket number
enabledUntick to leave the test out of every run without deleting it
EditionsThe editions the test runs in; default both. The script is the same for all, {edition} is replaced by the edition's name
StepsOne step per line, e.g. "Open File > New project file". Use {axis} for matrix values
Expected resultWhat must be true at the end. Every part becomes a check in the script
TODOWhy a test can't be automated yet, e.g. "cannot be automated". Leave empty otherwise
Test projectsThe projects whose files the test uses, see below
Test matrixAxes with comma-separated values; every combination is a separate run

Test matrix

An axis named platform with the values native, unix32 and an axis lang with C, C++ give 4 runs. A step like "Select platform {platform}" gets the value of each run. The runs are named after the test plus the values, e.g. Relative paths [platform=unix32, lang=C], and each one gets its own line in the report. The editor shows how many runs a matrix gives.

Test projects

A test project is a directory of files that tests use: source files, a .cppcheck project file, a .cfg file. They live in tests/projects/NAME and are edited under Test projects in the left column. Before every run the project is copied to a new empty directory, so a test always starts with the same files, even if an earlier test changed them. In a script the copy is {project:NAME}, or {project} when the test has only one project.

Changing a file in a project makes the scripts of the tests that use it outdated, because the script was made for the old files.

Scripts

A test runs only when it has an up-to-date script. Generate it with Claude once, check it, and from then on it is replayed without AI.

Generating a script

Open the test and press Generate script. gen.py starts the application with the test projects in place, and Claude does the test by hand: it looks at the accessibility tree, clicks and types, and checks the expected result. It then answers with a script. The script is replayed from scratch and saved in the test file only if that replay passes. When the replay fails, Claude is told why and tries again, 3 attempts in all. While a script is generated the editor is locked.

  • A matrix test is explored with the first combination. The script uses {axis} where the values belong.
  • When the application does not do what the expected result says, Claude still writes the script that checks it and marks that one check "observed_fail": true. The script is saved, and the test fails until the bug is fixed. That is a finding, not a broken script.
  • When the test can't be done through the GUI, Claude answers CANNOT: <reason> and no script is saved.

Read the generated script before you trust it, especially its expect steps: they decide what the test proves.

The script format

A script is a JSON list of steps. Each step has do (an action) or expect (a check), and a label in the words of the test that is shown when it fails. Elements are found by name (part of the accessible name, case-insensitive) and role, and if needed path, nth and exact.

[
  {"do": "click", "name": "Help", "role": "menu item", "label": "Open the Help menu"},
  {"do": "click", "name": "Contents", "role": "menu item", "label": "Choose Help > Contents"},
  {"expect": "visible", "name": "Cppcheck GUI help", "role": "dialog", "label": "A help window opens"}
]
StepWhat it does
do: click, rightclick, doubleclick, focus, hoverAct on an element; "mouse": true clicks with the mouse
do: settextReplace the text of an edit field with value
do: type, keyKeyboard input to the focused element; keys uses xdotool names like ctrl+o, Return
do: waitWait for an element to appear, or with "gone": true to disappear
do: restartQuit and start the application again; settings are kept
do: sleep, write, copyPause, write a file in {work}, or copy a file in a test project
expect: visible, goneAn element is shown, or is not
expect: stateAn element is or is not checked, enabled, focused, selected, expanded...
expect: valueThe value or text of a field equals something
expect: text, ocrText is (not) on the screen; ocr reads pixels with tesseract, for context menus AT-SPI can't see
expect: fileA file contains, does not contain or matches a regex
expect: alive, exitedThe application is still running, or has quit by itself with status 0
expect: captureSearch regex in an element and save group 1 as a name; {name} in the later steps is replaced by it, for text that changes such as the version

Checks and actions wait for their element up to timeout seconds, 5 by default. The placeholders {work}, {home}, {project:NAME}, {axis} and {edition} are replaced before the run, captured values when the capture step has passed. The full description is under How to write a script below the script in the editor.

Outdated scripts

A script is made for the test's steps, expected result, TODO, matrix and the files of its test projects. When any of those change, the script is OUTDATED: it is kept but skipped by every run, and the editor says so in red. You then have three choices:

  1. Generate script again.
  2. Approve the script when the change does not affect it, e.g. a typo fix in a step.
  3. Edit the script by hand in the editor; it has to be valid JSON before you can save.

Running tests

Every test starts a fresh application with an empty HOME and fresh copies of its test projects, so tests never depend on each other.

From the web interface

Pick the edition in the header first: opensource, premium or both. Then:

  • Run test in an open test runs that test, all its matrix combinations.
  • ▶ next to a test file runs every test in that file.
  • Run all runs every test in every file.

With "both", the run is done for one edition and then the other, and each edition gets its own report. The job box shows the test and step that is running and the results as they come. Stop ends the run at once: the test that was running is SKIP "aborted by user", and the report is written with the tests that are done. Only one job runs at a time.

From the command line

./run.py ~/cppcheck/build/bin/cppcheck-gui tests/application.json tests/projects.json --edition opensource
OptionMeaning
APPThe binary to test
FILE ...One or more test files
--edition opensource|premiumAPP is this edition; only the tests for it run. Without it all tests run and there is no history per edition
--test TEXTOnly tests whose name contains TEXT (case-insensitive)
--id IDOnly the test with this id, all its matrix combinations
--src DIRGit checkout for the SHA in the report; default the directory of APP
--out DIRWhere the run directories go; default results

run.py prints one line per test and the path of the report, and exits with 1 when a test failed, so it can be used in a script or CI job. Scripts are generated the same way with ./gen.py APP FILE.json; it takes --edition, --test, --id, --force (also tests that have a script), --model and --attempts.

What happens in a run

  1. The tests to run are selected: enabled, for this edition, not filtered out. Tests without a script, or with an outdated one, are SKIP.
  2. For each test, a new Xvfb session starts, the test projects are copied, and the application is started.
  3. The script is replayed step by step. After every step that acts on the GUI (click, type, key, settext, restart...) a screenshot is saved.
  4. At the end, or at the first failing step, the step log, a final screenshot and the application log are saved, and the log is searched for a crash.
  5. After the last test, results.json and report.html are written in the run directory.

Reading the report

Each run writes one self-contained report.html; read it top-down: the verdict first, then what changed, then the details of each failure.

PartWhat it tells you
HeaderFAILED or PASSED with the count, and the run details: date, edition, duration, git SHA ("+ uncommitted changes" when the checkout was dirty), branch, commit, application, host, test files
Number boxesPassed, failed (how many crashed the app), skipped, duration, and with history the change against the previous run
Results per test fileA bar per file, green/red/amber. Shows whether failures are in one part of the GUI. Only when the run has more than one file
The last runsPass, fail and skip counts for up to 15 runs of the same edition; the number on a column is its failures
Changed since the previous runNEW failures, tests that are fixed, and tests that are STILL FAILING
Status historyA row per test that did not pass in every run: "new failure", "failing since 10/22 12:00 (b8b27a)", "fixed since", "flaky: 4 changes", "never ran"
Failed and skipped testsA card per test: the reason, the step strip, the screenshots after the last 3 steps and the final screen with a red frame
All testsEvery test grouped by file, with its time, links to its files and its step screenshots

The step strip

Every test has a strip with a cell per script step: green passed, red failed, grey not run. A failure at step 2 of 14 usually means the test or the application broke early. A failure at the last step usually means one check is wrong, or the bug the check describes. Under the strip it says e.g. "failed at step 9 of 14", "not run" or "did not start".

Files in a run directory

A run directory is results/<date>-<time>-<edition>-<sha>/, e.g. 20261022-120317-opensource-b8b27a95/. The test name becomes the file name, with everything but letters, digits and _ turned into _.

FileContent
report.htmlThe report
results.jsonThe run details and every result. The history is read from these files
NAME.txtThe step log: each step, ok or FAIL, its time and its screenshot
NAME.pngThe screen at the end of the test, or when it failed
NAME.stepNN.pngThe screen after step NN, for steps that act on the GUI
NAME.app.logWhat the application printed

The history only uses runs of the same edition in the same --out directory that have a results.json. Runs made before 22 Oct 2026 don't have one and are left out. Tests are matched by name.

Troubleshooting

Start with the reason in the report and the final screenshot: together they usually say whether the application, the script or the test is wrong.

What you seeWhat it means and what to do
SKIP "no script"The test has no script yet. Generate one, or write it by hand
SKIP "OUTDATED SCRIPT"The test or one of its test projects changed after the script was made. Generate again, or approve the script if the change doesn't matter to it
FAIL "timeout waiting for element to appear"An element with that name and role wasn't found within the timeout. The reason lists the most similar visible elements and the open windows: a renamed button shows up there. Fix the name in the script, or regenerate
FAIL with observed_fail=True in the reasonClaude saw the application not do what the expected result says when it made the script. It is a known bug, and the test fails until the bug is fixed
FAIL with CRASHThe application was not running at the end of the test, or its log has a fatal message (SIGSEGV, SIGABRT, an assertion, AddressSanitizer, QFATAL...). A crash fails the test even if every step passed. Read NAME.app.log. A test that quits the application with status 0 is not a crash
FAIL "could not start"The session or the application did not start. Check that the packages under Getting started are installed, and that the binary runs
"flaky" in the status historyThe test changes between PASS and FAIL. Usually timing: give the slow step a longer timeout, or add a wait step before it
A context menu can't be foundSome menus are not in the accessibility tree. Check them with an ocr step and choose with key Down and Return
"path ... is outside the test directories"write, copy and file steps may only use {work}, {home} and the test project copies
Generate script or Run test is greyed outweb.py has no binary for the edition picked in the header, or the test is not for that edition. Run test also needs an up-to-date script

guitest.py

guitest.py is what Claude uses to drive the GUI, and you can use it by hand to look at the GUI the way a script sees it. The session lives in $GUITEST_STATE (default /tmp/guitest-<uid>/state.json).

guitest.py start ~/cppcheck/build/bin/cppcheck-gui
guitest.py tree --showing --depth 3
guitest.py click --name Help --role "menu item"
guitest.py screenshot /tmp/screen.png
guitest.py stop
